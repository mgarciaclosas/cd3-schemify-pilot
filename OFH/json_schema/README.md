# Our Future Health (OFH) — data dictionary as JSON Schema

Generated by the schemify method from the Our Future Health data dictionary v14, its codings v14 and the Baseline Questionnaire Logic v2.2, for the CD3 harmonisation project. Written for someone who has neither the skill nor the steward on hand.

## 1. What this package describes

Our Future Health (OFH) is a UK cohort. This package describes its participant-level data as it sits in the provider's Trusted Research Environment (TRE): one JSON Schema per table, covering the participant table, the baseline questionnaire, clinic and point-of-care measurements, participant geographies, eleven NHS-linked health-record tables, and the genetic data files. **26 tables, 1101 variables** (every variable in the dictionary; PC1–PC40 and the 25 ancestry regions are counted as separate columns). **No participant-level data is in this package or was read to build it**; real data lives only inside the TRE (D004), so validating real exports means running `tools/validate.py` there.

## 2. Layout and composition

```
common/defs.json            shared answer codes (-998, -3, -1, -4, -999)
<table>/<table>.schema.json the mother file: an array of rows; each row is the allOf of its category files, then the routing conditionals
<table>/categories/*.json   one file per category of variables (the questionnaire has one per section)
examples/<table>/           toy_valid.json, toy_invalid.json (+ ledger of seeded violations), warning fixtures
tools/                      validate.py, warn.py, warnings/<table>.warnings.json, requirements.txt
dictionary.html             the browsable data dictionary
playground-<table>.html     an in-browser validator for each table
VARIABLES.csv, ROUTING.csv  the variable inventory and the routing register the validator reconciles
```

A row is the `allOf` union of its categories. Each category lists its own columns, and the mother's single `unevaluatedProperties: false` rejects any column no category declares. Every column is `required`: a missing value is written in-band (section 4), never left out and never null.

## 3. Value-encoding conventions

- **Coded questions** list every code with the source's own label as a `oneOf` branch (`const` + `title`), plus a sentinel branch where the value can be absent. **Measures** use `anyOf`: a number, or a sentinel. **Sparse codings** (the dictionary's `is_sparse_coding = yes`) keep their labelled codes and also allow other values of the type.
- **Multi-select questions** are arrays in one field (`[0, 2]`); a question not shown is `[-998]`. Each option is also listed as a one-item `{const: [code], title}` branch so the dictionary page can show the options (D052; remove once the page library lists array `items`).
- **Bounds** reject the impossible, not the merely rare. Where the source states no range, none is asserted (D024); agent-decided plausibility ranges are warnings (section 6).
- **Titles** are the dictionary's own wording, verbatim. A description appears only where the source states extra explanatory text, and routed questions carry "Shown if …" with the logic file's condition (D040, D053). Codes and labels are never repeated in comments (D041).
- **Text and date columns** accept any string; the source states no format (D043). Long code lists assert only a format taken from the source's own codes.
- **Questionnaire versions:** `_1_x` columns belong to questionnaire v1 wording and `_2_x` to v2, and a participant who answered one version has -998 for the other's twin. The logic file describes v2 only; v1 has no routing (D019, D022).

## 4. Sentinel semantics

| Code | Meaning | Where it applies |
|---|---|---|
| `-998` | Not shown / not recorded: the source's NULL. A question the routing did not show; a measurement or reason that was skipped or does not apply; a linked-record field left blank (D021, D101) | every table, wherever a value can be absent |
| `"-998"` | The same, as a string, so text, date and coded-string columns keep their type (`not_recorded_text`) | text, date and string-coded columns |
| `[-998]` | The same for a multi-select question | multi-select questionnaire columns |
| `-3` | Prefer not to answer | questionnaire and participant codings that define it |
| `-1` | Do not know | questionnaire codings that define it |
| `-4` | Do not remember | questionnaire codings that define it |
| `-999` | Suppressed by the data provider | questionnaire and participant codings that define it |

`-7` ("None of the above") and `-10` ("Less than …") are substantive answers, not sentinels. `-998` is this package's own code: no OFH coding uses it, and it must be mapped from NULL when data leave the TRE tables (D021). The source's own placeholders inside linked columns (dates 1800-01-01 and 1801-01-01, 9998/9999 for elective wait, 3000/4000 for A&E times and the text code "Null") are kept as labelled values (D116). Two columns have no -998 because they always apply: `LIFESTYLE_DRIVE_HRS_1_1` and `SLEEP_HRS_1_1` (D070).

## 10. Open items to confirm with the data provider

- **Downstream consumer (D007).** Which system will use these schemas, and whether it needs a JSON Schema draft other than 2020-12.
- **Questionnaire v1 and versions (D009, D022, D030).** The logic file covers v2 only. The 72 v1-only variables (46 revised `_1` twins and 26 others) carry no routing. The steward will supply the v1 questionnaire; until then also unconfirmed whether v2, v2.1 and v2.2 share one logic file.

- **Clinic skips (D089).** The clinic `_SKIPPED` / `_SKIPPED_REASON` rules are read from the titles: skipped = 1 means the measurement is -998 and a reason is recorded; skipped = 0 means the measurement is recorded and the reason is -998. Can a skipped measurement have no reason, or an unskipped one still be blank (equipment failure)? If so these rules are too strict.
- **Blank fields in linked records (D101).** No logic file covers the eleven linked tables, so every non-key column permits -998. Which fields can really be blank needs a count from inside the TRE.
- **Genetic file headers (D125).** The ancestry proportion columns are named from the ancestry call labels; the real file headers must be checked in the TRE.
- **Imputed sample QC codes (D126).** The genotype array file lists M/F/U for genetic sex and v1/v2 for the array manifest; the imputed file lists no values. Ask the data provider whether the same codes apply.
- **Clinic and POCT abnormal threshold (R191).** The source says only abnormal first readings lead to a second set, and gives no threshold, so it cannot be checked.
